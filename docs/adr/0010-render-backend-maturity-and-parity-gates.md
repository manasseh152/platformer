# Render backend maturity and parity gates

The packetized renderer needed a production-readiness policy before GPU paths could become automatic/default backends: unsupported packets, missing assets, lighting semantics, or context loss must not silently drop required gameplay visuals. We chose Canvas2D as the reference backend, capability-driven backend selection, explicit backend maturity tiers, normalized fallback/degrade diagnostics, and parity gates for representative gameplay frames before GPU backends can be promoted. We also chose to continue maturing the custom packet-based renderer instead of migrating to Three.js because the project needs a 2D pixel-platformer pipeline tailored to tilemaps, native-frame presentation, fallback behavior, and deferred 2D lighting. Current backend and parity guidance lives in [`../patterns/rendering.md`](../patterns/rendering.md).
